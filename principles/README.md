# Product principles

This directory contains the 40-entry Product principle tree. Every principle has
**Ratified** catalog status. That status became effective when the repository
owner merged pull request
[#5](https://github.com/jrmoulckers/product/pull/5) on 2026-08-09, the act
described in
[decision record 0001](../docs/architecture/0001-ratify-product-principles.md)
and documented in the
[Ratification record](../docs/ratification/2026-08-09-product-principles.md).

[`manifest.json`](manifest.json) is the machine-readable catalog of every ID,
title, area, source file, and status. It is generated by
`scripts/build-manifest.ps1` and the repository validator fails if it drifts.
Tooling should read the manifest rather than parse these files. See
[CONSUMING.md](../CONSUMING.md) for how to cite these obligations.

## Reading the status fields

Two fields in every principle look like they disagree. They do not, because they
describe different things.

`**Status:** Ratified` is the principle's live catalog state. It is the only
field ratification changed.

The `**Owner and ratification:**` line ends `...and this proposal remains Draft.`
Its subject is *the proposal* — the source text of pull requests
[#3](https://github.com/jrmoulckers/product/pull/3) and
[#4](https://github.com/jrmoulckers/product/pull/4) — not the principle. That
sentence is frozen verbatim from those proposals and is deliberately never
updated. Freezing it is what proves ratification changed status and nothing else:
[decision record 0001](../docs/architecture/0001-ratify-product-principles.md)
commits that "only the 40 `Status` metadata values change from `Draft` to
`Ratified`," with ownership and Ratification wording byte-for-byte unchanged. The
repository validator enforces the frozen wording, and record 0001 is likewise
frozen at `Status: Proposed` because it records the proposal, not the outcome.

**Where the two appear to disagree, `Status` governs.** Every principle in this
directory is in force. A consuming repository citing one of these IDs is citing a
ratified, effective obligation.

Each principle records a stable ID, status, imperative, rationale, observable
verification, ownership and ratification, authority handoff, and exact legacy
input IDs or `none`. Legacy input references provide traceability without making
the legacy Studio wording authoritative here.

The exact catalog validator rejects deletion, renumbering, reordering,
unauthorized or mixed statuses, and any status-excluded semantic drift.

## Legacy input resolution

`studio-legacy:<document>:<n>` resolves to the `n`th numbered principle in the
legacy Studio `principles/<document>.md` file on `main`. The validator accepts
only IDs within the confirmed no-gap range for each registered legacy source.
Resolution confirms historical existence, not adoption or authority. These
references identify migration inputs; the legacy wording remains non-authoritative.
